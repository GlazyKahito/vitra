# VITRA device ingestion API

Research prototype. Not a medical device. Not clinically validated.

Devices (the Raspberry Pi enclosure, or the simulated adapter) push captured strip images to the
web app, which stores the image, runs the CV pipeline and creates an analysis run. The device never
talks to the CV service directly.

## Endpoint

`POST /api/ingest` — `multipart/form-data`

### Headers

| Header | Required | Meaning |
| --- | --- | --- |
| `X-Device-Id` | yes | Device **name** (`devices.name`, e.g. `VITRA-PI-01`, `SIM-01`), **not** the internal row id (`devices.id`, e.g. `seed-device-sim-01`). Looked up by name; `[A-Za-z0-9._-]{2,64}` |
| `X-Device-Key` | yes | Plaintext API key issued by *Devices → Rotate key*. Only its scrypt hash is stored (`devices.api_key_hash`). |
| `Idempotency-Key` | no | Opaque string (≤ 200 chars) unique per capture. A repeated key returns **200** with the existing run instead of creating a new one. Scoped per device. |
| `X-Capture-Timestamp` | no | ISO-8601 time the frame was captured on the device (`images.captured_at`, `analysis_runs.captured_at`). |

### Form fields

| Field | Required | Notes |
| --- | --- | --- |
| `file` | yes | JPEG, PNG or WebP, ≤ 15 MB. Magic bytes are checked; the declared type must match. |
| `sample_code` | no | Pseudonymous code (`[A-Za-z0-9._-]{2,40}`). Unknown codes create a sample; missing → next `S-YYYY-NNNN`. Samples created by a *simulated* device are marked `synthetic`. |
| `strip_product_id` | no | Defaults to `app_settings.defaultStripProductId`. |
| `strip_batch_id` | no | Must belong to the strip product. |
| `mode` | no | `research` (default) or `demo`. Demo must be enabled in settings. |
| `reaction_seconds` | no | 0–3600. Defaults to the strip product's reaction time (120 s). |
| `reaction_started_at` | no | ISO-8601. |

### Responses

| Status | Body | When |
| --- | --- | --- |
| `202 Accepted` | `{ "run_id", "run_code", "status" }` | Run created. `status` is the final pipeline status (`pending_review`, `calibration_required`, `invalid_image`, `failed`) — analysis is synchronous today. |
| `200 OK` | `{ "run_id", "run_code", "status", "duplicate": true }` | `Idempotency-Key` already seen for this device. |
| `401` | `{ "error": { "code": "unauthorized" } }` | Unknown device or wrong key. Failed attempts are audited (`ingest.unauthorized`). |
| `409` | `conflict` | Concurrent duplicate `Idempotency-Key`; retry to receive the existing run. |
| `413` | `file_too_large` | Payload or image > 15 MB. |
| `415` | `unsupported_media_type` / `unsupported_type` / `magic_mismatch` | Not multipart, or not JPEG/PNG/WebP. |
| `422` | `invalid_request` and others | Bad field values, unknown strip product, batch mismatch, demo mode disabled. |

Errors follow `{ "error": { "code": "<machine_code>", "message": "<human>" } }`.

### What the server does

1. Verifies the device key (scrypt, constant-time) and idempotency.
2. Validates the image (type, size, magic bytes).
3. Records a `capture_started` device event, then calls `startAnalysis(..., imageSource: "device")`:
   stores the original under `STORAGE_DIR/images/`, calls the CV service `/v1/analyze`, stores overlay and
   rectified strip PNGs, persists pads/colour features/quality checks, applies the result-state policy per
   analyte, writes `analyte_results`, sets the run status, and audits `run.create` / `run.complete`.
4. If the CV service is unreachable the run is stored with `status = failed` and every analyte `unavailable`
   — nothing is dropped, nothing is invented.

### Example

```bash
curl -i -X POST http://localhost:3000/api/ingest \
  -H "X-Device-Id: SIM-01" \
  -H "X-Device-Key: vdk_sim01_dev_key_do_not_use_in_production" \
  -H "Idempotency-Key: capture-2026-10-12T10-15-00Z" \
  -H "X-Capture-Timestamp: 2026-10-12T10:15:00Z" \
  -F "file=@strip.png;type=image/png" \
  -F "sample_code=SYN-0101" \
  -F "mode=demo"
```

The seeded simulated device `SIM-01` ships with the development key shown above so the endpoint can be
exercised locally. Rotate it (and never reuse it) on any shared deployment. `VITRA-PI-01` is seeded without a
key and has never connected; issue a key from the Devices screen before pairing the real enclosure.

### Device events

Real devices should also report heartbeats and faults; today the only inbound channel is ingestion, which
itself records `capture_started` / `capture_completed` / `error` events and updates `last_seen_at` and
`status` (`online` / `degraded`). Simulated devices stay `simulated`; their events are generated by
`simulateDeviceTick` and are labelled `[SIMULATED]` in the message and `simulated: true` in the payload.
